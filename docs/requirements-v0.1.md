# 1. 文書の目的

本書は、現時点で合意している歌詞作成補助ツールの要件を、v0.1 βの実装範囲として固定するための文書である。将来拡張は別管理とし、本書では「今作るもの」と「今は作らないもの」を明確に分ける。

v0.1 βは完成版ではなく、候補生成と語感評価の仮説を実際に使い、ユーザー本人の納得度フィードバックをもとに評価ロジックを改善するための検証版として位置づける。

# 2. プロダクト定義

## 2.1 目的

- 作詞中に、入力したキーワードから自力では思いつきにくい言葉へ連想を広げる。
- 「音が似ている」「意味や情景が近い」という異なる探索方向を、同じ画面上で扱う。
- 単なる類語辞典・韻検索ではなく、歌詞の発想支援ツールとして機能する。
## 2.2 v0.1 βの想定ユーザー

- 開発者本人のみ。
- 日本語での作詞を前提とする。
- Desktop利用を優先する。
- 複数ユーザー、課金、公開サービス向けの運用は対象外。
## 2.3 中心となる体験

| キーワードを入力<br>      ↓<br>10個の候補を見る<br>      ↓<br>「なぜこの言葉？」と思う<br>      ↓<br>詳細画面で2軸の位置と理由を見る<br>      ↓<br>新しい歌詞の発想につながる |
| --- |

# 4. 基本ユーザーフロー

初期画面：タイトル、キーワード入力欄、実行操作のみを基本とする。Enterキーでも実行可能。

生成：入力語を解析し、LLM等で40〜100語程度の候補を生成。候補数は性能・コスト・品質を見て調整可能とする。

評価：各候補を「語感類似度」「意味・文脈近接度」の2軸で0〜100点評価する。

選抜：単純な総合点上位ではなく、候補同士の重複を抑え、探索方向の多様性を考慮して10語を選ぶ。

結果表示：入力語と10候補のみを主に表示し、点数や理由は隠す。

詳細表示：別ビューで10候補をXY散布図に配置。Hover / clickでスコアと理由を表示する。

リロール：同一セッションの既出候補を原則除外し、別の連想経路から再探索する。

フィードバック：候補のLike / Dislikeと、β検証用の語感スコア納得度を記録する。

# 6. 評価モデル

## 6.1 2軸の定義

語感類似度：文字・意味ではなく、歌詞として発音したときの長さ、母音列、韻、特殊モーラ等の近さ。v0.1では「長さ > 母音パターン」を基本方針とする。

意味・文脈近接度：同義・類義だけでなく、同じ場面、情景、感情、因果、連想、比喩関係など、歌詞として接続可能な近さ。

## 6.2 v0.1での2軸の扱い

v0.1では語感類似度と意味・文脈近接度を同価値（50:50）として候補選抜に利用する。各軸の素点は独立して保持し、将来の重み付け変更で再利用できるようにする。

重要：ユーザーが将来重みを変更しても、各候補の語感スコア・意味スコア自体は変更しない。変化するのは候補生成・選抜における優先度である。

## 6.3 語感スコアの基本方針

語感スコアはLLMの主観採点に丸投げせず、標準的な距離指標と作詞感覚への補正を組み合わせるハイブリッド方式とする。基礎指標は再現可能なアルゴリズムで算出し、作詞向けの補正ルールを独立して適用する。

| sound_score =<br>  mora_length_score × w1<br>+ vowel_position_score × w2<br>+ edit_similarity_score × w3<br>+ lyric_adjustment<br><br>→ 最終値を 0〜100 に収める |
| --- |

初期重みはβ検証用の仮説値とし、実利用FBをもとに調整する。初期案は「モーラ長 40%、母音位置一致 25%、正規化編集類似度 25%、作詞補正 最大±10点」。固定仕様ではない。

編集類似度は、作詞用に正規化した母音・特殊モーラ列に対してレーベンシュタイン距離等を用い、0〜100へ正規化して使用する。

すべての構成スコアと補正値を保存し、『なぜこの語感点になったか』を後から追跡可能にする。

## 6.4 暫定的な長さ評価

長さは作詞時の置換可能性を重視し、モーラ数差に対して段階的な点数を付ける。初期案：差0=100、差1=70、差2=35、差3以上=0。β検証で変更可能とする。

## 6.5 意味・文脈評価

意味・文脈近接度は曖昧性が高いためLLM評価を主とする。LLMは候補ごとに0〜100点と短い評価理由を返す。プロンプト・モデル・評価基準は実装時に固定し、モデル変更時にも比較できるようバージョン情報を保存する。

# 7. 作詞用韻正規化 v0.1（暫定）

正規化ルールはv0.1で完全な言語学的正解を目指さない。個人利用のβ版として最低限のルールで実装し、実際の違和感事例を収集しながら追加・修正する。

## 7.1 データを3層で保持

| 1. 元の読み<br>   うんどう<br><br>2. 音韻解析<br>   [u] [N] [do] [u]<br><br>3. 作詞用正規化<br>   [u] [X] [o] [o] |
| --- |

元情報を上書きせず、正規化後の比較表現を別に保持する。これにより、将来ルールを変更しても元データから再計算できる。

## 7.2 暫定ルール

| ルール | v0.1の扱い |
| --- | --- |
| 通常母音 | a / i / u / e / o を基本単位とする。 |
| 長音「ー」 | 直前の母音を継承する。例：コーヒー → o-o-i-i。 |
| 促音「っ」 | 元分類は Q として保持。比較時は特殊モーラクラス X に写像可能とする。 |
| 撥音「ん」 | 元分類は N として保持。比較時は特殊モーラクラス X に写像可能とする。 |
| Q と N | v0.1では韻比較上近いものとして同一X扱いする。将来は Q↔N を部分一致（例:85%）に戻せる構造にする。 |
| 拗音 | きゃ・きゅ・きょ等は1モーラとして扱い、主母音 a / u / o 等を取得する。 |
| オ段 + う | 作詞用比較では o-u → o-o へ正規化する。例：どう → do-o。 |
| エ段 + い | 作詞用比較では e-i → e-e へ正規化する。 |

注：オ段+う、エ段+い等は歌唱・語による例外があり得るため、v0.1では暫定ルールとして扱う。

# 8. 10語選抜の考え方

最終10語は単純な総合点上位10件にしない。各候補の品質に加え、10語全体が同じ連想方向へ偏らないことを重視する。

「探索範囲が広い」とは、例として『夜中・深夜・真夜中・夜更け…』のように同じ意味クラスタだけで枠を消費せず、時間・視覚・感情・都市・抽象など異なる連想経路が含まれる状態を指す。

| 候補群<br>  ↓<br>2軸評価<br>  ↓<br>意味・連想上の近接候補をクラスタ化<br>  ↓<br>各クラスタから代表候補を選択<br>  ↓<br>「候補単体の品質 + 10語セットの多様性」で最終10語を決定 |
| --- |

具体的なクラスタリング方式・多様性ペナルティ・カテゴリ比率は設計フェーズで決定する。XY散布図上でも候補が一箇所へ不自然に密集しすぎないことを、選抜結果の納得度確認に利用する。

## 9.1 初期画面

## 9.3 詳細画面

- X軸：語感類似度 0〜100
- Y軸：意味・文脈近接度 0〜100
- 10候補を点として配置し、候補語ラベルを表示する。
- Hoverで2軸点数と短い理由を表示する。
- Clickで情報を固定表示できる構造を推奨する。
- β期間中のみ、語感スコア納得度FBを配置してよい。
# 10. リロール要件

- 同一入力語を保持する。
- 同一セッションで提示済みの候補を記録する。
- 既出候補は原則除外する。
- 前回とは異なる連想方向・クラスタを優先する。
- 候補枯渇時のみ既出語の再利用を許容する。
リロールは『同じ処理をもう一度』ではなく、『もう少し別方向を掘る』操作として定義する。

# 11. フィードバックとβ検証

## 11.1 候補評価FB

候補ごとにLike / Dislikeを記録する。これは『その候補を歌詞の発想として好むか』を測る。

## 11.2 スコア納得度FB

β版では語感スコアについて「低すぎる / 妥当 / 高すぎる」のようなFBを取得する。これは候補そのものへの好みとは別に、評価関数の妥当性を改善するためのデータとして扱う。

## 11.3 保存すべき評価コンテキスト

- 入力キーワード
- 候補語
- 生成回数 / セッション
- 語感スコアと全内訳
- 意味・文脈スコア
- 各評価理由
- 読み・モーラ・正規化列
- 候補Like / Dislike
- スコア納得度FB
- 評価ロジック / プロンプト / モデルのバージョン
## 11.4 v0.1 βで見る指標

| 指標 | 見ること |
| --- | --- |
| 語感スコア納得率 | 「妥当」の割合。 |

# 12. 個人チューニング方針

保存の主体は数値・構造化データとし、人間向け説明が必要な場合のみLLMで自然言語化する。

| --- |

# 14. 非機能要件

NFR-01 シンプルさ：通常利用時に不要な情報・設定を極力見せない。

NFR-02 再現性：語感評価は同一入力・同一ロジックで同一スコアを再計算できる。

NFR-03 説明可能性：候補の2軸点数とその根拠を確認できる。

NFR-04 観測可能性：スコア内訳、正規化結果、モデル/プロンプト/ルール版を追跡できる。

NFR-05 保守性：読み解析、韻正規化、語感評価、意味評価、候補選抜を独立モジュールとして実装する。

NFR-06 拡張性：2軸重み、正規化ルール、部分韻、フレーズ生成等を後から追加しても既存データを破壊しない構造にする。

NFR-07 応答性：作詞中に繰り返し使える待ち時間を目指す。具体的な目標値は技術検証後に設定する。

NFR-08 プライバシー：個人利用を前提に、入力語・FB等の保存先とLLM送信範囲を設計時に明示する。

# 15. 将来拡張（v0.1対象外）

将来機能は本要件とは分離してRoadmapで管理する。v0.1では後付け可能なデータ構造・モジュール境界のみ確保する。

2軸重み付けバー：「語感 ← 1 2 3 4 5 → 意味・文脈」の5段階。中央は50:50。各軸の素点は不変で、候補生成・選抜の優先度に影響させる。

部分韻 / フレーズ韻：例：『さよなら (aoaa)』と『後が無い (aoaa+i)』のような、長さ不一致・部分母音一致を扱う。

Preference反映：Like / Dislike履歴から数値嗜好を更新し、候補生成・選抜へ自動反映する。

高度な作詞用正規化：歌唱時の発音差、Q/Nの部分一致、語ごとの例外等を追加する。

多言語 / 公開対応：ユーザー増加が必要になった場合のみ検討する。

# 18. 設計フェーズへの引き継ぎ

次の設計フェーズでは、要件を増やすより、責務をモジュールへ割り当ててデータの流れを固定する。優先順位は以下とする。

1. システム全体アーキテクチャ：UI / API / LLM / 音韻処理 / DB の境界を決める。

2. 生成パイプライン：入力→読み解析→候補生成→2軸評価→クラスタリング→10語選抜→表示の処理順を定義する。

3. 語感評価エンジン：正規化、各サブスコア、補正、バージョニングを関数単位へ落とす。

4. LLMインターフェース：候補生成用と意味評価用を分離し、JSON出力仕様を固定する。
